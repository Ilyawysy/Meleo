# Meleo: инженерный разбор проекта

## Резюме

Meleo — функциональный прототип интеллектуальной платформы продуктивности.
Проект исследует, как объединить планирование, фокус-сессии, поведенческую
поддержку и измеримый прогресс в продукте, ориентированном на мобильное
приложение.

Результат представлен не как завершённый коммерческий сервис, а как
полноценная инженерная система: Flutter-клиент с offline-first данными,
FastAPI backend, доменная модель, AI-сценарии, admin SPA, миграции,
observability и CI.

## 1. Проблема

Обычный task manager отвечает на вопрос «что сделать», но слабо помогает в
момент, когда пользователь:

- не может начать сложную задачу;
- теряет контекст между планом и фактической работой;
- не видит накопленный результат;
- остаётся без приложения при нестабильной сети;
- получает от AI общий совет вместо ответа на основе собственных данных.

Продуктовая гипотеза Meleo: объединение фокус-контекстов, коротких
измеримых сессий, мягкой геймификации и контекстного AI снижает трение между
намерением и началом работы.

## 2. Цели

Проект ставит четыре инженерные цели:

1. создать mobile-first flow от задачи до завершённой фокус-сессии;
2. сделать основной UI работоспособным поверх локального состояния;
3. встроить AI в реальные данные пользователя с контролируемыми tools;
4. показать полный жизненный цикл системы — от миграции БД до мониторинга.

## 3. Решение

### Фокус-комнаты

Задачи группируются не в абстрактные списки, а в фокус-комнаты. Комната
задаёт контекст работы, содержит отсортированные задачи и чек-листы,
поддерживает архивирование и выбор активного пространства.

### Сессии и измеримый прогресс

`FocusSession` хранит плановую длительность, статус, награды и связь с
комнатой. `FocusTaskSegment` фиксирует переключения задач внутри сессии.
Завершение обновляет агрегаты и геймификационный профиль.

### Геймификация

XP, монеты, серии и recovery-механики дают обратную связь, но не заменяют
основной сценарий. Магазин и скины маскота используют заработанную внутреннюю
валюту и связывают визуальную персонализацию с выполненной работой.

### Контекстная помощь

В проекте реализованы два AI-подхода:

- focus statistics agent анализирует 28-дневный `FocusSnapshot` через
  ограниченный набор tools и стримит ответ по SSE;
- JITAI-flow «Не могу начать» собирает контекст текущего дня, задаёт
  уточняющий вопрос и предлагает небольшое действие. Формат ответа
  валидируется, а при ошибке используется fallback.

## 4. Архитектурный подход

Mobile хранит рабочее состояние в SQLite. Riverpod-провайдеры читают локальные
данные, а доменные команды сначала выполняют локальную запись. Операции чата и
уведомлений сериализуются через `DomainOperationQueue`, active-room provider
использует отдельную очередь. Доменные sync-сервисы самостоятельно отправляют
pending/dirty state, а `SyncOrchestrator` управляет их lifecycle и
агрегированным pull. При logout внутренний `ProviderScope` пересоздаётся, что
отделяет данные разных сессий.

FastAPI служит доверенной границей: проверяет JWT, вызывает доменные сервисы и
SQLAlchemy repositories. PostgreSQL размещается в Supabase; Redis разделён на
координационный instance и cache instance. Подробная схема приведена в
[architecture.md](architecture.md).

## 5. Наиболее сложные инженерные задачи

### Согласованность offline-first состояния

Локальная запись должна мгновенно появиться в UI, пережить сетевую ошибку и
быть подтверждена сервером без потери более нового изменения. Для этого
используются pending/dirty state, доменные push-сервисы, отдельные очереди там,
где операции требуют сериализации, версии, агрегированный pull и точечное
снятие pending state.

### Граница пользовательской сессии

Очистить secure storage недостаточно: в памяти остаются providers, timers и
sync callbacks. Logout orchestrator сначала останавливает синхронизацию, затем
пересоздаёт внутренний scope, очищает локальные данные и завершает auth
session.

### Управляемый AI

Модель не должна придумывать статистику или бесконтрольно вызывать доменные
операции. Snapshot ограничивает фактический контекст, registry определяет
доступные tools, JSON-schema валидирует JITAI, circuit breaker и Redis controls
ограничивают отказ и конкурентность.

### Наблюдаемость распределённого flow

`request_id` проходит через HTTP lifecycle, structlog формирует JSON-события,
Prometheus собирает метрики, а Grafana объединяет их с Loki. Это позволяет
исследовать не только UI-дефект, но и путь запроса до инфраструктуры.

## 6. Технологический выбор

| Технология | Причина выбора |
|---|---|
| Flutter | Единая mobile codebase и возможность platform channels |
| Riverpod | Явные зависимости и scope-based session isolation |
| SQLite / sqflite | Быстрое локальное чтение и offline-first модель |
| FastAPI | Async REST/SSE и типизированные контракты |
| SQLAlchemy + Alembic | Доменная persistence-модель и контролируемая эволюция схемы |
| Supabase | Managed PostgreSQL и Auth для прототипа |
| Redis | Разделение coordination и disposable cache |
| OpenRouter + LangChain | LLM streaming и structured tools |
| React + Vite | Компактная типизированная admin SPA |
| Prometheus + Loki + Grafana | Метрики, логи и единая диагностика |

## 7. Проверяемый результат

В showcase присутствуют:

- mobile, backend, admin и infrastructure исходники;
- история Alembic migrations;
- `241` проходящий backend-тест и `150` mobile-тестов на момент импорта;
- Flutter static analysis;
- TypeScript/Vite production build;
- GitHub Actions с path-aware jobs;
- документация архитектуры и ограничений.

Это позволяет оценивать проект по исходному коду и автоматическим проверкам,
даже если проверяющему недоступны закрытые credentials и внешние сервисы.

## 8. Ограничения

Честные границы текущего результата:

- billing подписки Pro не интегрирован;
- app blocking реализован только как Android-native прототип;
- AI требует внешнего провайдера и отдельной конфигурации;
- Celery пока не участвует в активном runtime;
- production topology не разворачивается из публичного showcase без закрытых
  значений;
- часть продуктовых сценариев требует дальнейшей проверки на реальных
  пользователях.

## 9. Что демонстрирует проект

Meleo показывает способность:

- проектировать связанный full-stack product, а не набор изолированных экранов;
- работать с offline sync и lifecycle конкурентных операций;
- моделировать домен и эволюцию PostgreSQL-схемы;
- безопасно связывать Supabase Auth с прикладными данными;
- использовать LLM с проверяемым контекстом, tools и fallback;
- строить CI и observability вокруг прототипа;
- различать реализованную систему и следующие этапы продукта.

## 10. Следующий этап

При развитии проекта приоритетны:

1. iOS parity для app blocking;
2. полноценный billing lifecycle;
3. расширение security и end-to-end тестов;
4. контролируемые эксперименты с JITAI и метриками эффективности;
5. deployment automation для отдельного демонстрационного окружения.

Главный результат текущего этапа — архитектурно целостный прототип, в котором
продуктовая идея воплощена в работающих потоках данных и доступна для
технической оценки.
